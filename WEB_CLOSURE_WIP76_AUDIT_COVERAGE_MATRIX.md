## Audit design requirements
- Every state-changing action must create an immutable audit event.
- Authentication/security events must be auditable.
- Configuration changes must record old/new values where safe.
- Reject and rollback require a reason and record that reason.
- Approval/rejection/rollback transitions are separate audit events.
- Permission/role changes record actor, subject, before/after effective access.
- Read-only access may be logged where required by security policy, but must not be confused with state-changing audit events.
- Audit records must identify actor, action, target, timestamp, result, correlation/request ID, and source context where available.
- Audit writes must be server-side and must not rely on client-submitted audit claims.
- Sensitive secrets/passwords/tokens must never be written to audit logs.
